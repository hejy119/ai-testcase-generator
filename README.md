# AI 辅助测试用例生成

用 Claude Code Skill + 项目知识库，把测试用例的产出从「每次从头写」变成「基于规范与风险沉淀生成」。

> **本仓库为脱敏演示版**：保留完整的机制与工作流，业务内容替换为虚构的「优惠券功能」。原项目服务于真实业务系统，因涉及公司资产不公开。

---

## 解决什么问题

手写测试用例有三个反复出现的损耗：

1. **重复劳动** —— 每个需求都要重新写列结构、编号、前置条件格式
2. **质量不稳** —— 不同人写的用例详略不一，预期结果常出现「功能正常」这类无法执行的描述
3. **重点不分** —— 最典型的是**用例均匀铺开**：高风险的核心逻辑和无关紧要的界面文案拿到同等笔墨。用例的价值在于覆盖高风险区，均匀分布恰恰是低价值的

前两条靠**规范 + 模板**解决，第三条只能靠**领域知识** —— 而 AI 恰恰不知道你的系统哪里容易出问题。

## 三个核心设计

### 1. 给范本、不给长篇规范

`references/测试用例模板.md` 只定义**形态**（11 列表格、每列放什么），`references/用例编写规范.md` 只定义**质量**（预期结果怎么写、哪些措辞禁用）。

职责严格分离 —— 改质量要求不会动到列结构，加列不会影响质量规则。

### 2. 风险地图：告诉 AI 该测什么

`knowledge/风险地图.md` 是本项目**最有价值的部分**。每个模块记录三样东西：

- **易错点** —— 按历史出问题的频次排序
- **历史缺陷** —— 缺陷号 + 摘要 + 教训
- **业务规则陷阱** —— 需求写了、但实现容易走偏的地方

生成时按风险倾斜用例预算。对照演示产出可以看到：订单金额计算（重灾区，含金钱计算）拿到 8 条、其中 2 条是历史缺陷回归；而纯展示类的用例只有 3 条。

**同样 30 条用例，有风险地图和没有，价值密度完全不同。**

### 3. 不许编 —— 防幻觉机制

AI 生成测试用例最危险的不是格式错，是**编造预期结果**：写一个看起来很合理的提示文案，但需求里根本没有。这种错误你审的时候很难发现。

三条机制防它：

| 机制 | 做法 |
|---|---|
| **禁用措辞表** | 禁止出现「功能正常」「符合预期」「数据正确」等无法执行的措辞，可机械扫描 |
| **可观测性要求** | 预期结果必须写清「**在哪看到什么**」—— 界面文案、跳转地址、字段值、日志关键字 |
| **待确认问题** | 需求没写清楚的地方**不猜**，列进「待确认问题」表并说明缺什么 |

演示产出里有 6 条待确认问题，其中 §REQ-1.4「优惠券叠加规则」需求本身就写着「本期先按一张订单只能用一张券处理」但没定义多券时的界面呈现 —— **这条用例没有被编出来，而是变成了一个问题**。

## 工作流

```
第一步  读模板与规范
第二步  解析需求 → 拆功能点清单 → ★ 停下等人工确认（硬闸门）
第三步  检索知识库（风险地图 > 术语表 > 历史用例 > 归档需求）
第四步  生成（预算向高风险倾斜；需求来源只能指向「当前」需求）
第五步  输出 + 维护需求索引
```

**第二步的硬闸门是关键**：功能点清单纯 AI 拆出来后必须经过人工增删才继续。这是整个流程里唯一能把你「知道该测什么」输进去的地方 —— 判断力不外包。

## 需求文档的生命周期管理

一个容易被忽略但很实际的问题：需求文档一直在增加，怎么组织？

```
需求文档/
├── 当前/     ← 用例的「需求来源」只能指向这里
└── 归档/     ← 只用于理解系统全貌，不能作为用例依据
```

**归档的触发条件是「被新版本取代」，不是「生成完用例」** —— 因为用例里记录的是文档路径，需求一转走，可追溯性就断了；而且需求评审后常要改要重跑，那时文档还得在「当前」。

**为什么要分开**：归档文档描述的是**已失效的旧行为**。AI 若把它当成现状，会生成断言已废弃行为的用例 —— 而且写得很像回事，很难发现。

`_需求索引.md` 由 skill 自动维护：写入时更新、读取时纠错（索引有文件没了 → 删行；文件有索引没有 → 补行），纠错动作必须报告给人，不静默修改。

## 目录结构

```
.
├── .claude/skills/gen-cases/
│   ├── SKILL.md                       # 五步流程
│   └── references/
│       ├── 测试用例模板.md             # 形态：11 列 + 列定义 + 文档骨架
│       └── 用例编写规范.md             # 质量：预期结果、禁用措辞、覆盖要求
├── knowledge/
│   ├── 风险地图.md                     # ★ 决定测什么、测多深
│   ├── 术语表.md                       # 领域术语，防止相近概念混用
│   ├── 需求文档/{当前,归档}/ + _需求索引.md
│   ├── 历史用例/                       # 避免重复生成、判断回归范围
│   └── 缺陷记录/                       # 缺陷库导出件，用于更新风险地图
└── output/                            # 生成产出
```

## 使用方式

在 Claude Code 中：

```
/gen-cases 优惠券功能需求-V1.2.md
```

或直接说「帮我给优惠券功能写测试用例」。

生成后你会拿到一个功能点清单，确认或增删后才开始写用例。

## 演示产出

见 [`output/优惠券功能-2026-10-04-testcases.md`](output/优惠券功能-2026-10-04-testcases.md) —— 32 条用例，其中：

- 11 列格式全部一致，编号连续
- 禁用措辞零命中
- 异常场景占比 47%（异常 15 条 + 边界 6 条，合计 66%）
- 6 条待确认问题，指出需求中真实的歧义

## 迭代记录

这个方案不是一次成型的，中途推翻过一次：

1. **初版设计过度** —— 8 个文件的完整体系（需求点追溯、覆盖矩阵、自检门禁、多版本 diff、导出脚本）。评审时被指出「维护成本全落在人身上」
2. **退回极简版** —— 1 个文件 35 行，只留三条最有效的规则
3. **跑完真实需求后发现真问题** —— 格式和防幻觉都达标，但**用例均匀铺开**，重点不突出
4. **转向风险驱动** —— 加风险地图，用例预算按风险倾斜
5. **补反馈闭环** —— 逃逸缺陷回灌风险地图、评审版回灌规范

关键认识：**AI 写用例的能力已经过剩了，稀缺的是「知道该测什么」和「知道上次哪错了」。** 这两件事都不在提示词里，在你的领域知识里。
