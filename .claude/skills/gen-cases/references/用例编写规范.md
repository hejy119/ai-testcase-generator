# 用例编写规范

本文件定义用例的**质量要求**：怎么写才算好。
表格结构、列的定义见 `测试用例模板.md`。

## 一、预期结果（最容易写废的一列）★

必须写清「**在哪儿、看到什么**」——具体到界面文案、跳转地址、字段值、日志关键字。

| | 例子 |
|---|---|
| 反例 | `提示错误` |
| 反例 | `登录功能正常` |
| 正例 | `页面顶部红字提示"账号或密码错误"，停留在登录页` |

**禁止出现的措辞**（预期结果与前置条件中均适用）：

```
功能正常  显示正常  无异常  符合预期  数据正确  结果正确  逻辑正确
正确显示  正确执行  处理正确  验证是否正常
合理  友好  良好  美观  流畅  稳定  及时  相关
```

写不出具体文案时 —— **不要编**。见下方第四节。

## 二、其余各列

**用例标题**
一句话说清「什么条件下做什么、期望什么」，能独立看懂。
禁止 `测试XX功能`、`XX功能验证` 这类没有信息量的标题。

**测试数据**
必须给**字面值**（`Abc@12345`、`13800138000`）。
禁止 `输入合法账号`、`输入有效密码`、`输入正确数据` —— 那不叫写了测试数据。

**测试步骤**
编号分步，每步一个动作，写明操作对象（`在"账号"输入框输入 zhangsan`）。
禁止 `进行登录`、`提交表单` 这类省略操作对象和数据的写法。
标准：一个不了解本需求的人，照着步骤能机械执行，不需要问你。

**前置条件**
要具体（`用户 zhangsan 已注册且状态正常`），不写 `系统正常运行`。
涉及数据的，说明数据的准备方式或初始状态。

**编号与优先级**
- 编号：`TC-` + 三位序号，本次文档内唯一、连续，且不与历史用例编号冲突
- 优先级：`P0`（核心功能，失败则系统不可用）/ `P1`（主要功能，失败影响主流程）/ `P2`（次要功能或异常分支）/ `P3`（边缘场景、体验类）

**粒度**
一条用例只验证一个意图。不把正常流和异常流塞进同一条；不把「登录成功 + 记住我生效」写成一条。

## 三、覆盖要求

用例集必须覆盖：

1. 正常流程（Happy Path）
2. 异常场景（Error Handling）
3. 边界条件（Boundary Values）
4. 权限校验（如有）

**异常场景占比不低于 30%。**

## 四、不许编（防幻觉）

这是本规范最重要的一条。

**需求没写清楚的地方，不要自己补。** 包括但不限于：具体提示文案、具体数值阈值、业务规则（如「连续失败 5 次锁定」）、超时时长、分页条数。

处理方式：把问题列进文档末尾的「待确认问题」表，说明**具体缺什么信息**。

「待确认问题」格式：

| # | 涉及需求条目 | 缺什么 | 影响 |
|---|---|---|---|
| 1 | REQ-1.4 | 密码错误时的具体提示文案未定义 | 该条用例的预期结果无法确定 |
| 2 | REQ-1.5 | 连续登录失败的锁定策略（次数、时长）未定义 | 「锁定」相关用例无法编写 |

依赖未确认信息的用例：可以写，但预期结果处标注 `阻塞-待确认`，让缺口可见。

**判断标准**：如果你写下的某个预期结果，你在需求文档里找不到依据，那是编的。
